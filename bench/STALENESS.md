# Staleness model: extracting signal from version-skewed benchmark data

## The problem

We will never have benchmarks for every (config × version). Old measurements
are the only data we have for most of the space. Throwing them away ("quarantine
everything old") wastes signal; using them naively ("a GB/s is a GB/s") lies.

This document defines principled rules for **how much to trust an old
measurement given what actually changed** — not wall-clock age, but code
identity.

## 1. Ground truth: code hash determines what was measured

A measurement is of a specific machine-code artifact, identified by
`(config, raidjit_version, code_hash)`. The `code_hash` (SHA-256 of the
generated bytes) is the ground truth for "did the kernel change."

When comparing a measurement from V1 against the current version V2 for the
same config, there are exactly four cases:

| Case | Condition | Meaning |
|------|-----------|---------|
| IDENTICAL | `hash(V1) == hash(V2)` | Same machine code. Measurement fully transferable. |
| NEUTRAL | hashes differ, change classified performance-neutral | Old measurement likely still valid. High weight. |
| RELEVANT | hashes differ, change classified performance-relevant | Old measurement is stale. Low weight or incomparable. |
| UNKNOWN | hashes differ, cannot classify | Conservative: low weight, flagged. |

## 2. Change classification

### 2.1 Levels

| Level | Name | Weight | Definition |
|-------|------|--------|------------|
| 0 | Identical | 1.0 | Code hashes match. Not a "change" at all. |
| 1 | Performance-neutral | 0.9 | Change cannot affect performance by construction. |
| 2 | Bounded-relevant | 0.5 | Performance-relevant but structurally bounded. |
| 3 | Structural | 0.2 | Algorithmic or structural change. Treat as incomparable unless explicitly needed. |
| 4 | Unknown | 0.1 | Cannot classify. Conservative default. Always flagged. |

### 2.2 What counts as performance-neutral (Level 1)

- Metadata-only changes: twin reporting, plan-ID formatting, error messages.
- Bug fixes in code paths **not taken** by this config (e.g. fixed an assert
  in the AArch64 backend; config is x86-only).
- Comment, whitespace, or debug-info changes in the emitter source.
- Changes to the *planner* that don't affect which code this config generates
  (verified by hash stability, not by reasoning).

### 2.3 What counts as bounded-relevant (Level 2)

- Different register allocation, same instruction sequence.
- Instruction substitution with same uop count (e.g. `mov` → `lea` for zeroing).
- Constant-pool layout changes without code changes.
- Small immediate-value changes.

### 2.4 What counts as structural (Level 3)

- Different loop structure or unrolling.
- Different twin implementation (the twin's emitter was rewritten).
- Algorithmic change (e.g. closed-form → generic recovery).
- ISA restriction changes that alter which code path is taken.
- Any change to the config-space validity affecting this config.

### 2.5 Classification sources (priority order)

1. **Manual annotation** (`bench/annotations/<sha1>-<sha2>.json`): a human
   classified the transition. Highest priority. Format in §5.
2. **Disassembly diff** (automatic): if both versions' disassembly is stored
   (see `bench/disasm/`), diff at the basic-block level:
   - No instruction changes → Level 1.
   - Same basic blocks, different registers/immediates → Level 2.
   - Different block structure → Level 3.
3. **Config-space signal** (automatic): if the transition's `config_space_version`
   bump touched this config's twin/ISA/gate → at least Level 3.
4. **Default**: Level 4 (unknown). Never assume neutral.

The classifier records **which source** produced the classification. Manual
annotations override automatic ones; automatic ones are recomputed when new
disassembly arrives.

## 3. Partial inference: don't discard the whole comparison

A benchmark result is a **comparison set**: N candidates measured together
under identical conditions. This is its real value — pairwise rankings are
more robust than absolute GB/s.

**Key rule:** freshness is per-candidate, not per-file.

For a comparison set measured at V1, evaluated against target version V2:

```
freshness(c, V2) = classification_weight(code_change(c, V1 -> V2))
```

A pairwise comparison (A vs B) is usable at V2 iff:

```
min(freshness(A, V2), freshness(B, V2)) >= USABILITY_THRESHOLD (default 0.5)
```

and carries:

```
comparison_weight(A vs B) = min(freshness(A), freshness(B))
                          × protocol_match(V1, V2)
                          × machine_trust
```

**Consequence:** if v1 measured (twinA vs twinB vs baseline) and v2 changed
twinA's code but not twinB's or baseline's:
- twinB-vs-baseline: both fresh → full weight, fully usable.
- twinA-vs-anything: twinA is stale → reduced weight or excluded.
- We extract the twinB signal. We do **not** throw away the file.

**Absolute GB/s values** (not just rankings) require stricter handling:
they're only transferred at Level 0–1. At Level 2+, absolute numbers are
dropped but the **ranking** may survive (a 5% register-allocation change
won't flip a 2× twin advantage, but we can't be sure about a 3% edge —
the trainer accounts for this via the noise margin).

## 4. Confidence decay: driven by change count, not wall-clock time

```
weight(measurement, target_version) =
    freshness
  × recency_factor
  × machine_trust
  × protocol_match
```

Where:

- **freshness**: from §2/§3 (0.0–1.0). The dominant term.
- **recency_factor**: `decay_base ^ num_relevant_changes`
  - `decay_base` = 0.9 (configurable in `bench/config.json`).
  - `num_relevant_changes` = number of versions between the measurement's
    version and the target where this config's `code_hash` changed at
    Level ≥ 2.
  - **Critical:** versions where the code did *not* change do not decay the
    measurement. A 2-year-old measurement of untouched code outranks a
    2-month-old measurement of code rewritten 5 times.
- **machine_trust**: per-machine reliability from `machine.json`.
  - Default 1.0. Bare-metal with many runs: up to 1.2. Noisy cloud VM: 0.7.
  - Adjusted by the aggregation tool based on observed variance.
- **protocol_match**: 1.0 if `bench_protocol_version` and `sizes_bytes` match;
  0.5 if protocol version differs but is manually mapped; 0.0 if incomparable
  (excluded, not down-weighted).

## 5. Manual annotations

When a human understands a transition better than the automatic classifier:

`bench/annotations/<from_sha7>-<to_sha7>.json`:
```json
{
  "from_version": "abc1234",
  "to_version": "def5678",
  "annotator": "carlo",
  "date": "2026-10-15",
  "classifications": [
    {
      "config_pattern": "twin=xorbit,isa=x86",
      "level": 3,
      "reason": "xorbit restricted to non-x86; x86 xorbit candidates no longer generated"
    },
    {
      "config_pattern": "isa=avx512",
      "level": 1,
      "reason": "only twin reporting changed in ui_meta.c; codegen untouched (verified by hash)"
    }
  ],
  "default_level": 4
}
```

`config_pattern` is a comma-separated `key=value` matcher against candidate
fields (`twin`, `isa`, `mul`, `plan_kind`, `topology`, `op`). All patterns are
evaluated in order; first match wins. `default_level` applies to unmatched
configs (default: 4).

Annotations are **versioned with the facility** (committed to the repo) and
**auditable**: the aggregation report lists which annotations influenced each
inference.

## 6. Explicit uncertainty: every value carries its provenance

No aggregated value is ever a bare number. Every inference carries:

```json
{
  "value": 1.23,
  "unit": "gbps",
  "uncertainty": {
    "sources": [
      {
        "raidjit_version": "abc1234",
        "code_hash": "deadbeef...",
        "weight": 0.9,
        "freshness": 1.0,
        "change_level": 0,
        "classification_source": "hash_match",
        "machine_id": "epyc-9d25-vm1"
      },
      {
        "raidjit_version": "def5678",
        "code_hash": "cafe1234...",
        "weight": 0.25,
        "freshness": 0.5,
        "change_level": 2,
        "classification_source": "disasm_diff",
        "machine_id": "zen4-baremetal"
      }
    ],
    "total_weight": 1.15,
    "assumptions": [
      "twinB code unchanged v1->v2 (hash match)",
      "v1 and v2 bench protocols match (sizes [64K, 1M])"
    ],
    "flags": ["CROSS_VERSION", "STALE_PARTIAL"],
    "confidence": 0.78
  }
}
```

**Flags** (machine-readable, always set when applicable):
- `CROSS_VERSION`: merged across raidjit versions.
- `STALE_PARTIAL`: some candidates in the comparison are stale (Level ≥ 2).
- `STALE_UNKNOWN`: any contribution was Level 4 (unknown change).
- `RETIRED_CONFIG`: config involves a retired twin/ISA/option.
- `LOW_WEIGHT`: `total_weight` below the trainer's minimum threshold.
- `SINGLE_SOURCE`: only one version's data contributed.
- `ANNOTATED`: a manual annotation influenced the classification.

**Confidence** is computed as:
```
confidence = total_weight / (total_weight + skepticism_prior)
```
where `skepticism_prior` = 1.0 (configurable). This means a single
low-weight source yields low confidence, while many agreeing sources
converge toward 1.0. It is **not** a p-value; it's a weight-normalized
measure of evidence mass.

## 7. Worked example

**Scenario:** v1 (2026-10-01) measured rs(6,3) encode on Zen4:
`(baseline: 95 GB/s, xorbit: 18 GB/s, ternlog: 107 GB/s)`. ternlog wins.

v2 (2026-10-11) restricts xorbit to non-x86 (config-space v1→v2) and fixes a
reporting bug (Level 1 for non-xorbit configs).

**Analysis for target v2:**
- `baseline`: hash unchanged → freshness 1.0.
- `ternlog`: hash unchanged (reporting fix didn't touch codegen) → Level 1 → freshness 0.9.
- `xorbit`: config-space restriction → Level 3 → freshness 0.2. Also flagged `RETIRED_CONFIG` for x86.

**Partial inference:**
- ternlog-vs-baseline at v2: min(0.9, 1.0) = 0.9 ≥ 0.5 → **usable**, weight 0.9.
  Conclusion: "ternlog beats baseline on Zen4 rs(6,3) encode" transfers to v2
  with high confidence.
- xorbit-vs-anything at v2: min(0.2, ...) = 0.2 < 0.5 → **excluded** from v2
  training. The v1 xorbit measurement is preserved as historical data
  (marked retired) but doesn't influence v2 heuristics.

**Result:** we kept the useful signal (ternlog wins) without pretending the
stale xorbit number means anything for v2.

## 9. Non-goals (explicit)

- **Predicting** performance for unmeasured configs (that's the static model's
  job; this facility only weights *measured* data).
- **Automatic codegen-drift bisection** (useful, but out of scope; the
  CODEGEN_DRIFT records make it possible later).
- **Real-time** updates (this is an offline batch facility; training runs are
  explicit, versioned, and reproducible).
